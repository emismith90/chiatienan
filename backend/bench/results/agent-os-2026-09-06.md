# The Agent OS branch on the benchmark (2026-09-06)

The nine Agent OS phases claim **zero behaviour change for the lunch bot**. The
golden fixtures prove that for `run_bot_turn` with a fake engine; this is the other
half — the real engine, the real model, the real graders.

Reproduce (needs `OPEN_ROUTER_KEY`; `bench.run` calls `app.agent.run_turn`, not
`run_bot_turn`):

```bash
cd backend
python -m bench.run --corpus typical --engine pi --repeat 3 --out bench/results/pi-typical-2026-09-06.json
python -m bench.report bench/results/pi-typical-2026-09-06.json
python -m bench.report --compare bench/results/pi-typical-r3.json bench/results/pi-typical-2026-09-06.json
```

## The headline

| corpus | turns | errored | `tool_selection` | `ledger_state` | `prose_quality` | p50 / p95 | cost |
|---|---|---|---|---|---|---|---|
| `typical`, `--repeat 3` | 69 | 0 | **69/69 = 1.00** | 55/60 = 0.92 | n/a (no judge) | 3.8s / 22.4s | $0.137 |

No judge model was configured, exactly as in the `pi-typical-r3.json` baseline, so
`prose_quality` is n/a on both sides and the two runs are comparable.

## Reading the comparison against `pi-typical-r3.json`

`bench.report --compare` prints 16 blockers. None of them is this branch:

**14 × MISSING — the `prod` corpus is absent by design.** The baseline ran 37 cases
(111 turns); this environment has 23 (69 turns). The 14 `p*` cases come from
`bench/corpus/prod_conversations.json`, which is real (pseudonymized) conversation
and is `.gitignore`d and never committed. A checkout without it cannot run them.
`--compare` flagging them as MISSING is the right reading of a partial corpus, not a
regression.

**`B2` — `ledger_state` 3/3 → 0/3, and it is not the branch's.** The same case on
`origin/main`, three reps, fails too — and fails *worse*: main drops the payer out
of `participants` (`tool_selection` fails as well, 0/3), where this branch keeps all
three participants and only differs on split policy, itemizing the bill photo
("ai ăn nấy trả") instead of splitting equally. Money is conserved either way
(261,000đ). Evidence: `pi-b2-g12-main.json`.

The baseline is from 2026-08-13 and `origin/main` has moved to 2026-08-26 on a
**floating** model alias (`~deepseek/deepseek-v4-flash-latest`), so the baseline
cannot attribute this to either tree; what it can say is that the branch is not the
cause, because main fails the same case in a strictly worse way.

**`G12` — the branch's rate is lower on a case both trees fail the same way.**

| tree | `ledger_state` on `G12` |
|---|---|
| this branch | 10/20 |
| `origin/main` | 15/20 |

(`pi-g12-r5-*.json` + `pi-g12-r15-*.json`; Fisher exact p ≈ 0.19 — not significant at
n = 20 a side.) The two failure modes are identical on both trees:

1. the `propose_meal` guard refusing a turn that looked up «Emi», «Emmy», «Emy»… and
   then left them out of both `participants` and `guests` — that guard is main's, not
   new here; and
2. a three-way split (66,668 / 66,666) of a meal the case expects split two ways,
   because "Emi rủ đi" (Emi *suggested* it) is `initiator`, not a participant.

**What the model is handed is byte-identical on the two trees.** Dumping the system
prompt, the rendered user message, the full tool manifest, the skills, the context
files, the model, the thinking level, the builtin tools and the caps for this case
on both trees and diffing them gives **zero lines of difference**. There is no path
by which the branch could steer this case differently, so the gap is sampling on a
hard case against a floating alias — but it is recorded here rather than rounded off,
because 10/20 vs 15/20 is not nothing and a bigger sample (or a pinned model id)
would settle it.

## Re-run after Phase 11 (the room CMS) — **fails the ship criterion, under investigation**

| corpus | turns | errored | `tool_selection` | `ledger_state` | `prose_quality` | p50 / p95 | cost |
|---|---|---|---|---|---|---|---|
| `typical`, `--repeat 3` | 69 | 0 | 67/69 = 0.97 | 57/60 = 0.95 | n/a (no judge) | 4.7s / 45.0s | $0.139 |

`--compare` against the Phase 10 run reports **2 blockers**, both on `B3`:

```
- `B3` · tool_selection · DROP — 1.00 → 0.33 (-0.67)
- `B3` · ledger_state   · DROP — 1.00 → 0.33 (-0.67)
```

**This is recorded as failing, not as noise, until the data says otherwise.** What is known
so far, separated into what was checked and what is still open.

### What the three B3 runs actually did

All three are the vision model reading a bill photo and choosing *people* wrong — not a
number the model computed:

| rep | outcome |
|---|---|
| 1 | put member 4 in `participants` when the case expects `[1,2,3]`. **The tool refused the call** — "Ghi theo món cần đủ giá của MỌI người trong bữa — còn thiếu: [4]". Nothing was written. |
| 2 | passed |
| 3 | picked payer 4 instead of payer 1 |

### Why Phase 11 is unlikely to be the cause (checked, not assumed)

Phase 11 touched five non-test backend files, and none of them is reachable from a turn:

- `app/main.py` — **purely additive**; the one removed line is the import line, and the five
  new routes are appended at the end.
- `app/roomcms.py`, `kernos/content/sources.py` — new modules, called only by those routes.
- `kernos/content/store.py` — `publish()` gained one optional kwarg defaulting to `None`,
  guarded by `if if_published is not None`. `publish` is not called during a turn.
- `kernos/osadmin.py` — the lunch profile does not enable `os_admin`, so none of it loads.

Direct check: `grep -rn "roomcms|store.publish|source_changes" bench/ app/chat.py app/agent.py`
returns nothing. `test_tools_manifest.py` (19 tools, in order) and the 9 byte-identical
golden fixtures both still pass, so what the model is handed is unchanged.

The `bills` cases have swung this way before in this same file: `B2` went `0/3 → 3/3`
between the Phase 9 and Phase 10 runs with no relevant code change, and `G12` moved
`1/3 → 2/3` in this very comparison.

### Resolved: B3 is a ~60% case, and `--repeat 3` cannot see it

`B3` re-run at `--repeat 15` on this tree (`pi-b3-x15-2026-09-06.json`):

| grader | passed | graded | rate |
|---|---|---|---|
| tool_selection | 9 | 15 | **0.60** |
| ledger_state | 9 | 15 | **0.60** |

At p = 0.6, three attempts give:

| outcome | probability |
|---|---|
| 3/3 | 0.216 |
| 2/3 | 0.432 |
| **1/3** | **0.288** |
| 0/3 | 0.064 |

So Phase 10's `3/3` and Phase 11's `1/3` are two ordinary draws from the same
distribution — together about half of all outcomes. Nothing regressed. Combined with the
code-path checks above (no Phase 11 code is reachable from a turn), **the two blockers are
noise and this run is clear.**

### The finding that outlives this run: the ship criterion is too weak for `bills`

This is worth more than the incident. For a case that truly passes 60% of the time, the
chance of `--repeat 3` producing a false blocker — 3/3 in the baseline, then <=1/3 — is
**0.076 per case per comparison**. Across 23 cases, several of them vision-dependent, a
spurious blocker is more likely than not on any given run. That also means Phase 10's
"`tool_selection` 1.00" was partly luck, and reading it as a hard 1.00 was generous.

Two things follow, neither done here:

1. **Raise `--repeat` for the `bills` cases**, or grade them over a pooled rate rather than
   per-run, before treating a bills blocker as signal.
2. **Record a per-case natural rate** (this file now has one for `B3`) so a comparison can
   say "within noise for this case" instead of "-0.67".

Until then the rule of thumb is: a blocker on a `bills` case is a prompt to re-run that
case at `--repeat 15`, not a reason to stop — and a blocker on a `week` or `meals` case,
which are deterministic, is real.
