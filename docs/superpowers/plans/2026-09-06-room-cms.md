# Phase 11 — the room's own CMS: view, edit, revision log, republish

Written 2026-09-06 on `claude/headless-cms-pi-harness-nn18pb`, after Phase 10.

**The ask.** A link in the room that shows the CMS of the agent that room runs. Anyone in
the room can view and edit it. Keep the revision log so a change can be traced. Add a way
to republish an existing version.

Unlike Phases 5–10, **this ships on**. It is a new door into the content plane, opened to
seven people who are not admins, on a bot that moves real money. The design work is
almost entirely about what that door does *not* open.

---

## 1. Facts from the code

1. **Server-side, most of this already exists.** What is missing is a room-scoped door.
   - `kn_profile_versions` **is** the revision log: `version`, `status`
     (`draft|published|superseded|retired`), the whole `spec`, `actor`, `note`,
     `created_at`, `published_at`. Read with `store.list_versions(profile_id)`.
   - `kn_audit_log` (`actor`, `action`, `entity`, `entity_id`, `before`, `after`, `at`)
     is written by `store.log(...)`.
   - **`store.rollback(profile_id, version, *, actor, gates, override_reason)` already
     republishes a superseded version**, skipping gates 3 and 4 because that version
     passed its probe and its eval when it was first published. Exposed today only at
     `POST /api/admin/profiles/{id}/rollback`.
   - Editing is `create_draft` → `update_draft(patch)` → `publish(gates=…)`.
2. **Two unrelated auth systems.** Room routes take `Depends(require_session)` → a bearer
   token → `AuthCtx(member_id, room_id, display_name, nickname)`, then `_check_room(ctx,
   room_id)`. The admin router takes `X-Admin-Password`, a shared secret, with a
   self-declared `X-Actor` header. **There is no admin identity** (design §9). A room
   member, by contrast, *is* identified — which is what makes an honest revision log
   possible here for the first time.
3. **Two vocabularies already govern who may change what.**
   - `gates.BLACKLIST_FIELDS` = `builtin_tools, models, tool_packs, pipeline, eval,
     extensions, settings, runtime, caps`. Enforced against **agent** actors (gate 5);
     a human publish may currently touch all of it.
   - `capabilities.SCOPE_VOCABULARY` = `prompt.body, prompt.append, skills, rules,
     validation.warn`.
   - A rule tagged `money` is refused to agents (`cms_draft_change`); a human may edit it.
   - Gate 2: a money profile with a risky builtin tool needs an `override_reason` on
     every publish — the lunch profile always does.
4. **Sources are upstream of drafts** (the Phase 8 lesson). `create_draft(snapshot=True)`
   pulls the business's current `kn_sources` into the draft. So a change written only to
   a version's `spec` is silently reverted by the next snapshotting draft.
   `approve_proposal` already handles this correctly via `_apply_source_changes`.
5. **The frontend has the pattern.** `side-panel.tsx` is a tab strip (`ledger`,
   `knowledge`) with both panels mounted and the inactive one hidden; the fetch is gated
   on the active tab so a room that never opens it never pays for it.
   `place-dialog.tsx` / `note-dialog.tsx` are the dialog pattern.
6. **The lunch profile is the business default**, shared by every space with no binding of
   its own. Editing it changes the bot in every such room.

## 2. Decisions

**D1 — "Edit" is scoped; "view" is not.** A room member may read the whole resolved
profile, including the parts they cannot change. They may write only
`prompt.body`, `prompt.append`, `skills` and `rules` — the `SCOPE_VOCABULARY` minus
`validation.warn` — and never a rule tagged `money`. Everything in `BLACKLIST_FIELDS` is
refused for a `member:` actor exactly as it is for an `agent:` actor.

*This is a deliberate narrowing of the literal ask and the user must confirm it.* Taken
literally, "anyone in the room can edit" lets any of seven people swap `models` (spends
money at a different rate, and gate 3 would demand a probe), raise `caps`, change
`pipeline`, or delete the money-safety rule that stops the bot doing arithmetic in prose.
The admin-password path keeps all of that. The room path does not. One constant
(`ROOM_EDITABLE`) widens it if the user disagrees.

**D2 — The actor is `member:<id>`.** Same form the Phase 10.3 proposal card already uses
for a confirm. This is what makes the revision log worth keeping: every version names a
real person, not `admin`.

**D3 — Optimistic concurrency on the published version.** The client sends the
`base_version_id` it loaded. If the profile's `published_version_id` has moved since,
the write is refused with 409 and the current version, rather than silently overwriting
another member's edit.

**D4 — An edit writes the source *and* the version.** Otherwise fact 4 bites: the next
snapshotting draft pulls the old source back and the room's change vanishes with no error
anywhere. Reuse the path `approve_proposal` uses.

**D5 — Republish is `store.rollback`, unchanged.** It already refuses anything that is not
`superseded`, already skips gates 3/4 with a recorded reason, and already writes a new
version rather than mutating history — so republishing v2 over v5 leaves v5 in the log.
The room route passes `actor="member:<id>"` and an `override_reason` naming the member,
because gate 2 demands one for this profile.

**D6 — The room edits the shared profile, and the UI says so.** The alternative —
copy-on-write into a room-specific profile on first edit — is safer in principle but
changes what the room is running, stops it tracking boot updates (`managed_by` leaves
`"boot"`), and needs a space binding. With one real room the practical risk is nil and
the honesty is cheap: the panel states, above the editor, that this bot is shared by
every room that has not been given its own. Recorded as the known limit, with
copy-on-write as the follow-up when a second real room exists. This is consistent with
the warning the Phase 10.3 proposal card already carries.

**D7 — No model-visible change.** This phase adds routes and UI. The prompt, the tool
manifest and the pipeline are untouched, so the benchmark does not need re-running for
the *phase* — only for whatever a member subsequently edits, which is their own doing and
what the revision log and republish button exist for.

## 3. Tasks

### 11.1 — the read API and the link

`app/main.py`, all `Depends(require_session)` + `_check_room`:

- `GET /api/rooms/{room_id}/agent` → `{agent: {slug, name, persona}, profile: {id, name,
  business}, version: {id, version, actor, note, published_at}, editable: {prompt_body,
  prompt_append, skills:[{name, description, body}], rules:[{slug, content, tags,
  editable}]}, readonly: {models, caps, builtin_tools, tool_packs, pipeline_stages},
  shared: bool, scope: [...]}`. `rules[].editable` is false for a money-tagged rule.
- `GET /api/rooms/{room_id}/agent/versions` → the revision log: `version`, `status`,
  `actor`, `note`, `created_at`, `published_at`, and `paths` (what changed against the
  previous version, from `gates.changed_paths`).
- `GET /api/rooms/{room_id}/agent/versions/{version}` → that version's editable content
  plus a unified diff against its predecessor (reuse `osadmin._unified`).

**Proof:** a member of the room reads it; a member of *another* room gets 403; no bearer
token gets 401; the money rule comes back `editable: false`; `shared` is true for the
seeded lunch profile.

### 11.2 — edit and publish

`PUT /api/rooms/{room_id}/agent/content`, body `{base_version_id, note, prompt_body?,
prompt_append?, skills?, rules?}`:

1. Refuse if `base_version_id` ≠ the profile's current `published_version_id` (409).
2. Build the patch from the supplied fields only. Refuse any blacklisted path and any
   money-tagged rule with a message naming the field (400).
3. `create_draft(from published, snapshot=False)` → `update_draft(patch,
   actor=f"member:{id}")` → write the changed sources → `publish(gates=…,
   actor=f"member:{id}", override_reason=f"room edit by member:{id}", note=note)`.
4. Return the new version and the paths it changed.

**Proof:** a prompt edit publishes and the next turn's system prompt contains it; a skill
edit is still there after a later snapshotting draft (D4); `models` in the body is
refused; a money rule is refused; a stale `base_version_id` is refused with the current
version; the audit log and `kn_profile_versions` both name `member:<id>`; a gate failure
(e.g. an empty prompt body if gate 1 refuses it) leaves the published version untouched.

### 11.3 — republish

`POST /api/rooms/{room_id}/agent/versions/{version}/republish`, body `{note?}` →
`store.rollback(profile_id, version, actor=f"member:{id}", gates=…,
override_reason=f"republished from the room by member:{id}")`.

**Proof:** republishing a superseded version makes it the published spec again as a *new*
version number; the version it replaced becomes `superseded` and is still in the log; a
`draft`/`retired`/currently-published version is refused with the reason; the room's next
turn uses the republished content.

### 11.4 — the frontend

- `side-panel.tsx`: a third tab, `Agent`. Fetch gated on the active tab, like `knowledge`.
- `agent-panel.tsx`: the shared-bot notice; the editable fields (prompt body, append
  lines, skills, rules) with money rules shown locked and labelled; the read-only block
  (model, caps, packs) shown but not editable; the revision list with actor, when, note
  and changed paths; a version opens its diff; a **Republish** button on any superseded
  version, with a confirm.
- `lib/api.ts`: the four calls. `use-room.ts`: bump a version counter on a successful
  write so the panel and the chat both refetch.
- Tests in `src/components/chat/__tests__/agent-panel.test.tsx`.

**Proof:** the panel renders from a fixture; the money rule has no editable control;
saving calls the API with the loaded `base_version_id`; a 409 shows a "someone else
changed it, reload" message rather than retrying; Republish asks first.

## 4. Open questions for the review gate

1. **D1** — is a scoped room editor right, or should "anyone can edit" mean literally
   everything, with the gates as the only guard?
2. **D6** — shared profile plus a warning, or copy-on-write into a room-owned profile on
   first edit?
3. Is there a path by which a room member's edit can defeat the money invariants —
   through `prompt.body` (the whole system prompt is in scope), a skill body, or a
   non-money rule that contradicts `money-safety`?
4. **D4** — is writing sources on a room edit correct, or does it have a failure mode the
   proposal path does not (it changes the business's future drafts, and the business is
   shared with the poker profile's room)?
5. Does republish need to be narrower than `rollback` (which skips gates 3 and 4) when the
   actor is a room member rather than an operator handling an incident?
